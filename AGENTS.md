# Vera Development Constraints

These rules apply to the entire repository.

1. Read [PRODUCT.md](./PRODUCT.md) before starting any task. Treat it as the sole authoritative product context.
2. Before modifying UI, obtain the corresponding Mike page or saved Mike screenshot as visual truth. Record a same-size Mike/Vera comparison for acceptance.
3. Reuse existing Mike pages, routes, data contracts, and components by default. Vera-specific UI is a minimal legal capability increment, not a parallel design system.
4. Before adding a table, state, page, panel, or general framework, demonstrate that the existing task, artifact, document, citation, review, or Matter objects cannot carry the requirement.
5. Every feature must shorten completion time, improve work-product quality, improve source verification, or control a consequential final action. If it satisfies none, do not implement it.
6. The normal path shows work and outputs. Security, local-storage, permission, hash, and audit detail appears only for exceptions, export/egress, or explicit expansion.
7. Do not change APIs, permissions, security boundaries, authentication, export gates, or legal disclaimers merely to support a UI adjustment.
8. Preserve unknown and unrelated untracked files. Do not clean, move, stage, or delete them.
9. UI acceptance must cover same-size Mike/Vera screenshots, keyboard operation and visible focus, long Chinese text, 125% and 150% zoom, and responsive behavior. Keep the primary workflow recognizable as Mike.
10. Without a defined threat model or explicit user need, do not add encryption, permission, audit, security state, or security pages. Do not remove existing authentication, authorization, Keychain storage, Matter ownership, or file-path validation.
11. Do not promote hashes, internal IDs, `local-first`, or encryption in ordinary UI. Keep factual notices when selected cloud models send content off-device.

## Litigation UI Constraints

These constraints apply to every civil and commercial litigation screen, prototype, and Figma change.

12. Mike is the visual authority for the application shell, navigation, spacing, typography, controls, density, and interaction vocabulary. A Patent frame is only a secondary scaffold: verify every borrowed top-level region against the corresponding Mike page before reuse. If no exact Mike page exists, use the nearest Mike shell and interaction pattern, record the gap, and never treat Patent as an independent source of truth.
13. These constraints do not authorize a litigation-only application, persistence model, or parallel design system. `Patents` and `Litigation` may have peer Practice-area landing pages inside the shared Mike shell. Those pages only discover, start, and resume Matter-owned work; execution, review, editing, sources, and delivery remain in the existing Assistant, Matters, Library, Tabular Review, Workflows, Work Tasks, Word, and Artifact surfaces. A Practice-area landing must not silently create a second product stack, local navigation system, or domain-specific route family. Any broader exception must satisfy Rule 4 and be explicitly approved.
14. Before creating or structurally changing a litigation Figma frame, record a preflight table in the task notes or artifact README. It must identify: the Mike source page and node; lawyer role; procedural stage; primary decision; input scope; final editable Artifact; canonical object mapping; one-interaction conclusion-to-source path; demo fixture identifier; and, for every inherited top-level region, pane, tab, table, column, status group, and action, its source node, `keep`, `adapt`, or `remove` decision, target purpose, canonical object, and rationale. Do not perform the structural Figma write while any required field or inherited region is unclassified.
15. A Patent screen may be cloned only after the Rule 14 preflight. One-for-one terminology replacement is prohibited. Reusing a visual component does not authorize copying its domain objects, table columns, status taxonomy, pane proportions, or review decisions.
16. Do not flatten claims, defences, issues, facts, legal elements, burdens of proof, evidentiary sufficiency, source verification, and lawyer-review progress into one table level or status field. Before displaying a badge, filter, status, or progress count, define its single semantic axis and allowed values. Separate party position, factual dispute, evidence sufficiency, source verification, and workflow progress.
17. A Case Map must preserve the relationship `issue -> legal rule or element and burden -> each party's position -> supporting and opposing evidence -> source and locator -> gap or conflict -> provisional assessment -> next lawyer action`. Do not substitute a flat `C/D/I + Status` matrix for that relationship.
18. Keep legal authorities and case-record evidence explicitly typed. A legal proposition links to an authority citation with an article, paragraph, or judgment locator; a factual proposition links to a record document, exhibit, testimony, or event with a page, paragraph, exhibit, or timestamp locator. They may share a source inspector only when type and role remain visible.
19. Every litigation screen must state its procedural stage and user-side role where they affect the work. First instance, appeal, retrial, and enforcement must not share generic tasks, deadlines, standards of review, or deliverables. The screen's primary decision and next action must be valid for the stated stage and role.
20. Create or designate one coherent, realistic, anonymized demo fixture before composing the UI. Every fact, date, party, role, document name, record locator, and procedural event must resolve consistently within that fixture. Every legal authority must be verifiable. Label synthetic case records as demo data and never fabricate legal citations. Include material conflicts, uncertainty, missing evidence, and an identifiable next litigation deliverable instead of perfectly tidy filler.
21. On litigation workbench and review screens, the largest interactive region must contain the lawyer's primary work product. On launch, setup, and completion screens, it may instead contain the single next-step flow or finished Artifact. Supporting panes may select inputs, verify a source, or review and deliver an outcome; they must not become a dashboard of equally weighted cards, pills, labels, and progress indicators.
22. Give every pane or tab one visible role: select inputs, edit the primary work product, verify a source, or review and deliver an outcome. If two regions serve the same role, merge or remove one unless the second provides a clearly labeled distinct action. Do not duplicate progress, selection, source chips, or status merely to fill space.
23. Action labels must name both the lawyer operation and its consequence, such as `Add to defence outline`, `Open cited page`, `Create evidence request task`, `Keep unresolved`, or `Export Case Map to Excel`. Distinguish adding to an internal draft, creating a task, exporting a file, and sending externally. External or irreversible actions require explicit confirmation; a button labeled `Request...` must neither silently send nor merely create an unlabeled note.
24. Represent litigation evidence through the existing Matter, Document/Version, Citation and, where needed, Tabular Review, AgentTask/Step, ArtifactLink, and Review Decision records. Litigation concepts may be derived fields or views over these contracts. They do not authorize a parallel Evidence Center, evidence graph, route family, table, or persistence object without satisfying Rule 4.
25. Before calling a litigation frame optimized, final, or implementation-ready, record the result of: domain-model realism; one coherent end-to-end lawyer workflow; stage and role validity; duplicate information and overlapping navigation; semantic-axis separation; selected-object synchronization; direct source and page verification; same-size Mike/Vera comparison; realistic long Chinese content; keyboard and visible focus; 125% and 150% zoom; and narrow-window behavior. If domain model, end-to-end workflow, source verification, or selected-object synchronization is Failed or Pending, the frame must not be called optimized, final, or implementation-ready. Any other pending acceptance item requires the frame to be labeled exploratory and not implementation-ready.
26. When review identifies a structural or domain error, correct the information model before adjusting color, decoration, or micro-spacing. Visual polish must not conceal an unresolved workflow problem.

## Agent Reliability Constraints

27. Keep Matter ownership, fixed document/version targets, source and template immutability, mutation idempotency, and approval/export gates as server-enforced hard boundaries. Do not weaken them to accommodate a model or provider.
28. The server owns execution orchestration: preload or deterministically resolve the bounded target and fixed sources where practical, validate and bind mutation targets server-side, and never make a provider-specific named-tool sequence a quality gate when the same work can be safely orchestrated by the server.
29. Classify provider capacity, timeout, protocol, and recoverable structured-output failures separately from work-product defects. Preserve completed effects and pause a resumable step with a clear recovery path; do not label them as a failed legal result.
30. Run deterministic checks immediately after creating or editing an Artifact. A bounded automatic repair may address concrete, safely scoped gaps, but a remaining repairable quality or citation gap must preserve the Artifact and enter the existing lawyer review path rather than discard the Task.
31. Use the existing AgentTask, Step, ArtifactLink, Citation, checkpoint, and Review Decision contracts for recovery and review by default. Do not add a parallel reliability state, table, page, or dashboard unless those objects cannot represent the requirement.
32. Citation-only verifier recovery must not ask a model to rewrite an entire Word deliverable. A server-owned marker patch is permitted only for one fixed current DOCX Version with current Matter source pins, one continuous exact source quote per contiguous `1..N` ref, and one unique non-heading paragraph anchor; it may add or replace only the proven `[N]` marker and must prove that the accepted-view body is textually unchanged after markers are removed. Any missing, drifted, conflicting, multi-anchor, or semantically unprovable mapping preserves the existing Artifact and enters the existing lawyer-review path; substantive content gaps alone may use the existing bounded document-edit path.
33. New verifier-repair routing must use server-owned structured issue codes and facts. Human-readable reasons are display text and a compatibility fallback only when the structured field is absent; a present but empty or malformed field must never authorize a mutation.
34. `clean_pass` and `review_required` describe verification outcome only. Approval and export remain governed by the existing Review Decision and fixed current Version/hash controls.
35. An uncalibrated content-grounding heuristic may be persisted only as a bounded observation. It must never become a hard verification gate, repair or mutation authorization, Task-status transition, Review Decision input, approval/export condition, or a claim that a conclusion is unsupported.
36. Named-tool orchestration is provider-neutral: every adapter that supports the contract must precheck an unambiguous registered name, force the current required name, and validate exactly one completed call before callbacks or dispatch. A wrong, missing, or out-of-sequence call fails closed; provider compatibility failures pause the existing Task resumably and never weaken Matter, version, idempotency, approval, or export controls.
37. Structured-output recovery may normalize only mechanically provable provider drift. It may fill a schema-required nullable field with `null`, separate a rule id from its identical supplied version suffix, or rebind a citation identifier only when the server has fixed the exact Document and Version and the citation quote is one continuous exact substring of that preloaded source. It must not add, remove, merge, or change a legal finding, outcome, recommendation, proposed clause, source quote, lawyer decision, or approval state; any unprovable remainder preserves the existing Task and enters its resumable review path.
38. A lawyer disposition has one server-owned meaning across prompts, Word mutations, opinions, progress counters, and verification: `accept` adopts the fixed proposed text, `comment` preserves the operative text and records the fixed lawyer direction or recommendation, and `skip` preserves the operative text without a document action. Free-text “other” input is a comment/direction unless the product explicitly asks for literal replacement text; never describe it as an applied revision.
39. Contract replacement automation must bind one unique exact source span to replacement text intended for that same span. If the source quote is only a fragment but the proposed text is a whole clause or sentence, preserve the Artifact and require bounded lawyer editing instead of producing duplicated wording, punctuation, or mixed governing-law/forum clauses.
40. A Contract Playbook opinion is not verified by finding identifiers alone. The current opinion body must deterministically align each material rule with its persisted lawyer disposition and, where present, exact lawyer direction or adopted proposed text. A semantic mismatch preserves all deliverables and routes only the opinion through bounded repair or lawyer review; it must never yield a clean pass.
41. A partially generated litigation Evidence Inventory remains one idempotent Task-owned Tabular Review. Exhausted source-bound generation for an individual finding must keep completed cells, restore only the unproven cell to pending, link the existing Review, and enter the existing lawyer-review path with a structured issue code; it must not discard or duplicate the Review, invent a quotation, mark an unreviewed finding verified, or label the legal result failed.
42. A structured lawyer revision must bind one complete decision set to the fixed analysis receipt, target Version, reference Version, and material finding identities before execution. A free-text review note may explain the request but must not authorize or infer `accept`, `comment`, `skip`, replacement text, a source target, or any document mutation.
43. Revising a Task-owned deliverable appends a new current Version to the same fixed Document and updates the existing Artifact identity through idempotent effects. It must not create a duplicate deliverable Document or parallel ArtifactLink merely because the Task is resuming, retrying, or processing a lawyer revision. Historical duplicates discovered from an earlier defect remain non-current evidence until a separately approved cleanup proves they are unreferenced.
44. A domain verifier must evaluate only the authoritative source and citation snapshots named by its fixed receipt or Pack contract. UI actions, retry routing, approval gates, and export gates must read the structured verifier outcome and issue codes; words such as `gap`, `pass`, or `failed` in human-readable summaries are display text and must never override a present structured result.
45. Approving a Task-owned Tabular Review must bind the current final-verifier identity and the database-owned live Review revision. Server-generated export bytes must be conditionally created at the database-planned deterministic storage path and read back without overwrite; the approval transaction must revalidate that binding and create or recover one fixed Matter-owned DocumentVersion. Final export may read only the latest approved fixed Version. A client-generated export, a reread of the live Review, a legacy identity-only snapshot, or a Tabular Review artifact ID masquerading as a Document ID must never authorize final export.
46. Structured Required Input must bind one complete response set to the fixed Task, Step, attempt, and request identity. Multiple required answers are submitted atomically; duplicate, stale, partial, or drifted submissions fail closed. A structured lawyer decision must not be represented by an invented free-text message or attachment merely to cross an execution boundary.
47. Effect idempotency compares the fixed semantic identity of the Task, Step, attempt, operation, input, and target; wall-clock fields such as creation timestamps are persisted metadata and must not turn an exact replay into a conflicting effect. Transition RPC parameter types must match their persistent database column types, and each changed fence requires a transaction-rollback SQL smoke using the real current types.
48. Repository schemas at a PostgREST boundary must accept the database's real `timestamptz` wire representation, including explicit offsets and microsecond precision. Tests must include that real representation. Canonical receipts and hashes retain the exact persisted value rather than silently rounding or rewriting it.
49. Artifact currentness is discriminated by Artifact type. A Draft is current only through its fixed Matter-owned current DocumentVersion. A Tabular Review is current only through its fixed Task-owned Review, owner, Matter, row protocol, current Step attempt/effect, and bound review revision; it must never be required to have or be treated as a DocumentVersion.
50. Public AgentTask snapshots may omit internal ownership fields such as `user_id`, but server execution, review, approval, and export code must receive the authenticated owner identity through an explicit typed argument or private internal context. Never recover an authorization fact from a public response DTO. Boundary tests must use the actual public snapshot shape and prove both the matching-owner path and the cross-owner rejection path.
51. Server-owned Work Tasks are bounded background jobs, not interactive thought-stream surfaces. Keep provider-side thinking disabled; create the bounded output first, then apply deterministic postconditions, the domain Verifier, and at most the existing bounded repair path. Do not spend unbounded reasoning tokens or extend a deadline merely to wait for a model to decide whether to call the fixed mutation tool.
52. A fixed Artifact mutation Step permits one authorized provider tool turn. Once the server commits that effect, it must stop provider iteration, recover the same-attempt committed effect before any later model call, link the one fixed Artifact, and continue to postconditions. A provider summary, timeout, retry, or duplicate call after the committed effect must not create a second Artifact or turn preserved work into a failed legal result.
53. After a domain adapter has produced a Task-bound, source-Version-bound, lawyer-reviewed accepted-view, downstream drafting consumes that accepted-view as its evidence input. Do not reattach the raw sources or unrelated prior generated documents merely to force another provider `read_document` sequence. The server retains the source pins and exact-quote verification; the provider receives only the bounded data needed for the current deliverable.
